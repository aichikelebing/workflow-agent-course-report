## 3 · 助手

建议把题目收窄为 **《论文去重时，下一步查什么？——Workflow 与 Agent 决策边界的对照实验》**。

这个题目抓住了一个容易被忽略的问题：两条论文记录的题名很像，系统查了作者，发现一侧信息缺失，于是改查发表会议。**仅凭这段运行记录，能判断它是 Workflow 还是 Agent 吗？** 两者都可能走出完全相同的路径。值得研究的是，**谁决定了下一步，以及把这个决定交给模型，究竟有没有改善去重结果。** 这样既保留了你们关心的“真实界限”，也把报告落在数据挖掘中的具体任务——实体匹配上。

## 一、实验怎么做

选用公开的 **DBLP–ACM 论文匹配数据集**。它包含两个来源的论文记录，提供题名、作者、发表刊物或会议、年份四个字段，以及 2,224 对已知匹配关系。我们可以直接用这些对应关系核验系统有没有把同一篇论文认出来。已有研究也考察过大模型做实体匹配的能力，我们可以在这个基础上专门研究“模型该如何获取判定所需的证据”。 [数据集][benchmark] · [实体匹配研究][matching]

给三个系统同一对论文记录。开始时只显示题名，每次查询可以查看两条记录的同一个字段，最多查两次。最后，三组都用**同一个判定器**，根据已经看到的字段回答“是否为同一篇论文”。两次查询是我们人为设置的实验条件，目的是让“下一步查什么”成为一个有代价的选择。

| 实验组 | 谁决定下一步 | 如何运行 |
|---|---|---|
| A．固定顺序 Workflow | 程序预先指定 | 例如先查作者、再查年份。具体顺序在预实验中选定 |
| B．条件分支 Workflow | 程序根据反馈执行预先写好的规则 | 例如作者高度一致就提前结束，作者缺失就查会议。规则在正式测试前定稿 |
| C．有限自主 Agent | 模型根据当前已见证据逐步选择 | 每次可选择查作者、年份、会议或结束。工具返回结果后，模型再次决定，直到结束或用完预算 |

**最重要的比较是 B 和 C。** A 和 B 的差异告诉我们，增加条件分支本身有没有用；B 和 C 的差异才回答，把已有证据交给模型，让它逐步选字段，能否超过一套认真设计的规则。Anthropic 的工程文章也把路由和带反馈循环的系统列入 Workflow，因此“会改道”“会循环”都不足以单独划出边界。我们只讨论**字段查询这项局部决策权**，结论的范围清楚。 [技术文章][agents]

## 二、原创点放在哪里

我建议把原创贡献集中在一个**可复核的配对实验**上。报告里可以把它完整拆成三步。

1. **只改变一条反馈。** 从测试集中取出若干对作者字段完整的论文，为每对制作两个版本。题名、会议、年份和真实匹配关系都相同，唯一变化是其中一个版本遮去一侧作者。在这项配对测试中，统一让三组先查作者，观察收到不同反馈后的第二步。人工遮盖的样例单列，和原始数据上的成绩分别报告。
2. **把可选动作都试一遍。** 第一轮结束后，只剩“查年份”“查会议”“立即结束”三种选择。实验结束后，可以离线重放这三条路径，交给同一个判定器核验。这样就能回答一个比“Agent 改道了”更有价值的问题：**它改查会议，真的挽回了一次误判吗？还是查年份也行，甚至当场停止也能答对？**
3. **把收益和代价一起报告。** 主表列出去重 F1、误合并数、漏合并数、平均字段查询次数和模型调用次数。案例分析优先选 B、C 判断不同的记录，展示两组看到了什么、选了什么，以及这个选择是否改变结果。如果规则达到了相同效果，或者模型多查了一次却把原本正确的结果改错，这些同样是有价值的发现。

这套设计里，**采用公开数据和现有模型属于实验基础；由我们设计的“改变一条反馈，再重放其余选择”才是报告应当详写的原创部分。** 它能把“谁控制流程”和“这种控制值不值得”分别用证据回答，也不用预设 Agent 一定获胜。

## 三、按什么顺序推进

| 阶段 | 具体工作 | 留下的成果 |
|---|---|---|
| ① 收到模板后定稿 | 把研究问题、原创点和实验表格映射到老师要求的栏目 | 一页实验方案、报告目录 |
| ② 做小规模预实验 | 先取约 10 对，包含同篇异写、题名相似但实际不同的论文。确认任务有区分度，并据此确定 A 的顺序和 B 的规则 | 样例、规则、提示词和修改理由 |
| ③ 冻结方案，正式运行 | 建议另取约 80 对，包含匹配对和题名相近的非匹配对；按论文实体隔开预实验与测试，三组使用完全相同的测试对 | 样本编号、模型版本、逐步日志、原始结果 |
| ④ 分析并成稿 | 先整理三组结果，再做配对重放，最后选案例解释差异。说明结论适用于这组候选论文和查询预算 | 一张主结果表、一张配对结果表、典型案例及局限 |

## 四、怎样满足老师的核查要求

**聊天记录应从本轮选题讨论开始留。** 建议在 GitHub 仓库中把 `conversations/` 和 `runs/` 分开。前者按时间顺序保存**完整的人机可见问答原文**，包括你提出的疑问、我们放弃的方案、改错过程和最终修改。每段对话结束就导出或逐条原文转存为 `.md`，核对首尾和轮次，避免最后只能凭记忆整理。后者保存实验中三个系统查了哪些字段、得到什么反馈、做出什么判定。老师从前者看你们怎样形成想法，从后者核验实验结果。
